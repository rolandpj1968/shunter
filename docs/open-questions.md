# Open questions from the daemon

*Ambiguities and gaps in [`PROTOCOL.md`](../PROTOCOL.md) that writing the store, the daemon and the adapters brought out. Each says what the code does today, so that nothing was decided silently. A question marked **Answered** is settled in code, with the reason; the protocol should state the answer. One marked **For the owner** is a choice the code has made provisionally and the owner should make.*

## The state machine

1. **A green train whose landing check can't be read.** T12 and T23 cover a reading that matches and one that doesn't. They don't cover no reading at all, when the forge keeps failing. **Today:** the daemon retries with backoff, escalates to J3 after its budget, and keeps retrying. The train stays green and holds the chain. Should T23 also void it at a deadline, as no verdict?

2. **A push whose deadline passes with its outcome unknown.** **Answered.** A push is idempotent, and a lander settles an unknown outcome by reading trunk. The git adapter reads trunk before each try and after the last one: trunk at the head is success, trunk anywhere but the expected base is a permanent refusal, and only then does it push, under a lease on the base and only when the head descends from it. A push whose answer was lost is therefore success on the next read, and never a second, different landing. The protocol should say so in §5.1 "landing".

3. **A second flake.** **Answered (owner): the rerun's failure is evidence in its own right.** §5.5 allows a known flake or a timing failure one rerun. When the rerun fails the same way, the daemon now treats it as class 4: it asks blame again with the class forced (`adapter.Reblamer`; the GitHub adapter runs the blame hook with `"force_class": "deterministic"`, and the example hook then skips its flake test and names lines by files). A line blame names goes back to its owner without a judge; blame that names none, or all of several, goes to J1, as before. A CI adapter that can't blame again, or a hook that answers any other class, names nobody. §5.5 says so.

4. **Hold from offered.** No row holds an offered line (L8–L10 start from waiting, waiting-for-base and parked). A cut-over import must carry holds, so it runs the gate on each line at once and holds the line after the gate accepts it. Should L8 also start from offered?

5. **A head that moved before the gate.** §5.2 doesn't say whether a change pushed between its offer and the gate is refused or taken at its new head. **Today:** the gate takes it, with a head-moved event before the acceptance.

## Judgement points and deadlines

6. **Deadlines with no number.** **Answered, with defaults the owner may change.** The protocol gives J1 10 minutes, J2 15 minutes and J5 one day. T2 ("the builder's deadline"), T6 (the pull request), T7 ("no verdict at the deadline") and the push had none. They are now keys of the configuration file ([`examples/shunter.toml`](../examples/shunter.toml), `[deadlines]`), with these defaults: builder 30 minutes, pull request 10 minutes, CI 90 minutes, push 5 minutes, one adapter call 2 minutes, a park that can't be tested 24 hours. Each adapter call is also bounded inside itself: a few tries with backoff (`[retry]`), each with its own deadline, before the daemon's own retry and J3. The protocol should give T2, T6, T7 and the push a default each.

7. **Does a rerun restart the CI deadline?** A rerun ordered at J1 (T11) re-enters testing, so its clock restarts. A rerun after a flake stays in testing, so its clock doesn't restart. Should it?

8. **"The same test failed in the previous batch, with unrelated changes"** (J1's default). The machine records a failure's evidence as one string. **Today:** "the same test" means the same evidence string. "The previous batch" means the failure recorded just before, kept in the store. "Unrelated" means no line in common. The CI adapter now gives the blame hook the structured check runs (name, conclusion, started time, link), and the hook may answer the evidence; a structured identity for a failing test is still the protocol's to define.

9. **Parks whose condition can't be tested.** §6.4 says such a park "carries a deadline", but names none. J1's default park has the condition "deadline: the judge reviews", with no time. **Today:** a condition `landed:<line>` is tested, and every other park is restored after 24 hours, with an alert. Should the protocol require every park to state its deadline as a time?

10. **J2 has no trigger in the machine.** "Two consecutive batches with unrelated changes failing on the same test, or the nightly run failing" isn't an event yet. J1's default park covers the first half in practice. The second half needs a trunk-health watcher (L3) to post an event.

## The CLI

11. **"cancel --action drop".** In the protocol, "dropped" means withdrawn by the owner (L29–L33). An abort can only requeue, park or return a line (§5.9). **Today:** `drop` returns the line to its owner with the reason, which matches what the old queue meant by it. The name may mislead.

12. **What an abort's park restores on.** An abort that parks needs a restore condition (L24). The CLI gives one: a deadline of the default park lifetime, "or a restore by hand". The CLI has no `restore` verb yet. Should it?

## Restarts and versions

13. **A log written by an older version.** At start, the store replays the log after its last snapshot through the current `Next`. If the current version refuses an event the old one accepted, or decides different effects for it, the store refuses to start, with an error naming the cause. A clean stop always writes a snapshot, so an upgrade after a clean stop replays nothing. §7 says a new version is "checked before it's started". Is refusing to start the right reading of that, or should the snapshot win?

14. **Watching the daemon itself (L3).** **Answered.** The daemon records alerts in the store and sends them to the judge, and the notifier appends every notice, alerts included, to an events file. `shunter watch`, run from a timer, watches the daemon from outside, sharing no code path with its loop: the store's lock held, the socket answering a command that runs in the loop, no restart loop, no effect or live train past its deadline plus grace, lines not stalled, the trunk lock not stale. It raises each finding through the notify hook ([`cutover.md`](cutover.md), "Watching"). Poll errors are still only the daemon's log.

## From the adapters

15. **A cancelled run.** **Answered.** A check run that ends cancelled, skipped, stale, neutral or needing action, with no check failed, is no verdict (§5.5 class 0): the train is void and its lines go back, nobody charged. This is the old queue's charged-on-a-cancelled-run defect, closed by construction: a cancel can't become a failure, because a failure needs a check that concluded `failure`. A run with only timeouts is timing (class 3), one rerun. The protocol's §5.5 should name these conclusions.

16. **No fail-fast.** The CI adapter reads a run as pending until every required check has completed, so that blame sees every failure, not the first. The cost is the time the rest of the run takes after the first failure. The old queue made the same choice.

17. **A hook is advice, and silence from it is no verdict.** A pre-flight hook that crashes, hangs past its deadline, or prints no JSON has caught nothing: the build fails as infrastructure, the daemon retries it, and in the end the train is void with no verdict. It never charges a line. A blame hook that fails leaves the failure unblamed, which goes to J1. A blame hook can say a failure is a flake, infrastructure or no verdict, or name lines of the train; it can't make a failed run pass, and lines it names that aren't in the train are ignored. The protocol could state, in §5.4 and §5.6, that hooks are advisory in exactly this way.

18. **Rebase or merge.** **Answered (Roland, 18 Nov): rebase stays the default.** A train is built by replaying each change's own commits onto the train (`strategy = "rebase"`, the default: a linear trunk, as the old queue did) or by merging each change's head (`"merge"`: the change's commits land unchanged, with a merge commit each). Either way trunk only fast-forwards to the train's tested head. Rebase gives a linear trunk but new commit ids, so the forge doesn't see a change as merged: the forge adapter labels and closes each change of a landed line itself. Merge keeps the ids, and the forge marks the change merged on its own. `strategy = "rebase"` remains the default, and `"merge"` remains available.

19. **The rerun's key.** A rerun's key can't be stored on the forge, so the CI adapter takes a run on the head that is already going as this rerun (asked twice, or started by hand), and reruns only completed, unsuccessful runs. A rerun whose answer was lost, and whose run then completed again before the retry, is rerun a second time. That costs a CI run and judges nothing wrongly.

20. **Train branches.** **Answered (Roland, 18 Nov): delete a train's branch once the train ends.** Shunter force-pushes `<prefix><train>` for each train. The forge adapter now prunes: whenever the live trains change, and every ten minutes, it deletes every branch under the prefix whose train is no longer live. A train 2's pull request is based on train 1's branch, and deleting a pull request's base closes it, so every open pull request based on the branch is first retargeted to trunk. A branch that is still the head of an open pull request is left for a later prune, so that the train's closing, with its reason, comes first. Pruning is housekeeping outside the machine: it is safe to repeat, and a failure is logged and tried again a minute later. A read-only forge (shadow running) refuses it.

21. **The changes of a stack before the base lands.** **Answered (Roland, 18 Nov): retarget a stacked change whose base has landed.** The forge names a change's base by its branch. Two places now retarget to trunk. When a line lands, every open change stacked on one of its changes, and not itself in the line, is retargeted before the landed change is closed, so that deleting the landed change's branch can't close it. And the gate, finding a change stacked on a change that has landed and is in no live line, takes it as before and retargets it. The gate's retarget is advice: the change is taken whether or not it succeeds. A base that closed *without* landing is still refused, and so is a base branch with no pull request (`branch:<name>`): nothing says it landed. With `strategy = "rebase"`, a retargeted change's branch still carries its base's original commits; the rebase drops those whose patch is already on trunk, and a base whose commits changed in its train (a conflict resolved) leaves a conflict, which the line's owner resolves by rebasing.

22. **What shadow running can't see.** Shadow reads the forge now, not as it was. Its comparison of CI outcomes is sound for history only as far as the checks on a head don't change once complete. That holds for a train's head until it lands; once it lands, it is trunk's head too, and other workflows (a nightly run) add their checks to the same commit. The CI adapter now reads only the configured workflow's check suites, and, with required checks named, counts only the suites that hold them (question 23). A rerun of the train's own workflow after the live verdict still changes what shadow reads; shadow does not yet cut the checks at the live verdict's time, because a train log carries no time for it. Its gate is sound only for the lines waiting now. It has no record of when the live queue took each line, so it can't compare the joining rule's choices with the live queue's for past trains; it reports which trains Shunter would assemble from the lines waiting now.

23. **Which checks on a head are the train's.** **Answered.** A commit carries the check runs of every workflow run on it. Once a train lands, its head is trunk's, and a nightly or push workflow's failures sit beside the train's own passing checks. Counting them read a landed train as failed (a false alarm in shadow). The CI adapter now reads only the check suites of the configured `workflow`'s runs on the head; and, when `checks` are named, the verdict's evidence (failures, timeouts, the checks blame reads) is only the checks in the suites that hold the required ones. A required check whose suite the forge doesn't give leaves every check counted, as before. §5.5 could say that a verdict is read from the train's own run, not from the commit.

24. **Capping a train by changes.** **Answered.** `max_lines` counts lines, and a stack of six changes is one line. `[queue] max_changes` now also caps the changes in a train, every change of a stack counted; 0 or unset is no cap. A line past the cap is skipped, as §5.3 skips a line that must ride alone, and a line that alone reaches the cap rides alone, so that it doesn't wait for ever. **For the owner:** a script queue may let some lines not count towards the cap (documentation only, say). Shunter can't tell that from a change's id and head; it would need the change's files from the forge at the gate, and a rule naming what doesn't count. Not done.

25. **Leaving a line out for more than a conflict.** §5.3's assembly leaves a line out only when it conflicts with the train. A script queue may also leave out a change that doesn't build when added to the train, or whose generated parts clash with another's (two schema migrations taking the same number). In Shunter that is a pre-flight step, which blames, by bisection or by files, rather than leaves out: the line is returned to its owner as charged, with the step's evidence, and the rest of the train goes on. The difference is whether the owner is told "your change broke the train" or "your change didn't fit this train". **For the owner:** should a pre-flight hook be able to answer a leave-out (`"left_out": {"<line>": "<why>"}`), taken as a conflict is? That widens what a hook can say, and so §5.4 and the leave-out rows, and is not done.

26. **Pre-flight blame per step.** **Answered.** The example pre-flight hook's steps each say how a failure is blamed: `"blame": "files"` (the default), `"bisect"`, or `"none"`, which names nobody, so that J1 decides (its default splits the train). A team whose old queue split a batch on a gate failure keeps that rule unchanged by marking the step `none`. The protocol is unchanged: a pre-flight failure that names no line is unblamed, as from CI.

## Lines and stacks

27. **Lines as a dependency graph.** **For the owner.** A line does two jobs: it orders changes (a stack's upper change needs its lower one) and lands them atomically. Most stacks need only the first, and a line that does both makes an older, independent change wait on failures in newer changes stacked on it. [`dependency-graph.md`](dependency-graph.md) evaluates replacing lines, as the unit of ordering, with needs derived from ancestry, keeping "line" as the name of the landing unit (one change, or a declared group of changes that co-require one another). Its first step: a stacked line waits in the queue, not for its base to land; the joining rule takes it when everything it needs has landed, rides earlier in the chain, or is earlier in the same train, and skips it when a need was skipped; a line whose need is returned goes back with it, uncharged. It also covers false edges from stacking for convenience, and the cost of a producer check per change. **Today:** the interim owner rules (question 28) hold, and the code is unchanged.
